# Stratos Wallet

**A production-grade frontend system built to demonstrate senior and staff-level engineering.**

Stratos Wallet is not a tutorial project. It is a fintech application engineered to the standard expected at companies like Stripe, Coinbase, Ramp, Shopify, and Vercel — with the architectural documentation to prove every decision was intentional.

---

## What this project demonstrates

| Capability | Demonstrated by |
|---|---|
| **Vertical slice architecture** | `features/` directory, each slice owns its own components, hooks, queries, and tests |
| **Contract-first development** | GraphQL schema defined before any component; types generated by codegen |
| **Ledger-first data model** | Balances, history, and analytics are all computed — never stored |
| **Real-time reliability** | WebSocket with sequence numbers, deduplication, missed-event replay |
| **Resilience engineering** | 15+ chaos presets, error boundaries, retry strategy, partial failure isolation |
| **Observability** | Structured logging with trace IDs, sequence gap detection |
| **State management** | React Query with cache namespacing, optimistic mutations, rollback |
| **Fintech realism** | Idempotency keys, pending states, transfer reviews, duplicate submission handling |

---

## Why it's built this way

Most demo fintech apps store a `balance` field. Real financial systems don't. Your bank records every debit and credit, then derives your balance by summing the ledger. This project follows the same principle.

The result: balance history, spending charts, and analytics are all projections of a single append-only ledger. Add a new analytics feature and you never touch the core data — you write a new query against the same source of truth.

This is **event sourcing applied to the frontend data layer**. It is a pattern used by every major financial platform, and it is the kind of thinking that separates a staff-level interview answer from a senior-level one.

## Architecture at a glance

```
src/
├── features/               Vertical slices — one per business domain
│   ├── auth/               Authentication, session management
│   ├── wallets/            Wallet list, wallet creation
│   ├── accounts/           Account detail, balance display
│   ├── transactions/       Transaction feed, infinite scroll, real-time updates
│   ├── transfers/          Fund transfer flow, idempotency, optimistic UI
│   └── dashboard/          Balance trend chart, spending breakdown
│
├── shared/                 Cross-cutting concerns
│   ├── hooks/              useWebSocket — reliability layer (seq, dedup, replay)
│   ├── logger.ts           createLogger() — structured logging with trace IDs
│   ├── api/                GraphQL fetcher, query client configuration
│   └── components/         Error boundaries, loading skeletons
│
├── chaos/                  Chaos simulation system
│   ├── ChaosContext.tsx    Config state, 15+ failure presets
│   └── ChaosPanel.tsx      Development control panel
│
├── mocks/                  MSW mock layer
│   ├── data.ts             Single-store data model — wallets, accounts, ledger
│   ├── handlers.ts         GraphQL and REST handlers with chaos injection
│   └── auth.ts             User registry, token generation
│
└── graphql/
    ├── schema.graphql      Contract-first schema — written before any component
    └── generated.ts        Codegen output — never edited by hand
```

## Reading this documentation

Every page in this documentation follows the structure of the [technical writing course](https://www.youtube.com/watch?v=5tmdStkXMDc):

- **Definitions** are written term-first: what a thing is, what class it belongs to, and what distinguishes it from alternatives.
- **Processes** use numbered steps in imperative form: "Define the schema. Generate the types. Implement the hook."
- **Decisions** are documented as ADRs (Architecture Decision Records): context → decision → alternatives considered → consequences.
- **Failure modes** are documented as tables: what fails, how the UI reacts, how it recovers.

Nothing was built without a reason. Every reason is written here.
